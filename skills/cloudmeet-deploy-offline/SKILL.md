# CloudMeet 离线部署包产出技能

目录约定：服务端及依赖从`deploy/release/<amd64|aarch64>/{server,dependencies}/`交付，客户端独立从`deploy/release/clients/<架构>/<批次>/`交付，clients与amd64、aarch64同级。完整包通过材料/架构/配置引用/摘要校验即可输出release，附INSTALL、来源与前置条件；不要求安装测试。不得重建deploy/debug，不删除其他历史材料，已有批次不因文档更新而迁移。完整规范仅由deploy/AGENTS.md负责。

按 **收集打包参数 → 生成内容清单 → 用户确认 → 逐工件获取/构建并报告 → 组装校验 → 交付报告** 执行。历史实例只是排坑证据，不是默认地址、平台或内容。本次仅要求编写方案/评估时不执行构建，也不连接任何服务器。

**工作区规范优先。**先读根AGENTS及deploy/AGENTS，README仅导航，references不覆盖规范。请求release/部署包默认完成编译组包、材料完整性校验和本地包交付，不包含测试环境、安装或运行测试。维护源deploy/skills/cloudmeet-deploy-offline，安装副本同步使用。

## 0. 固定交付边界与防跑偏

编译、打包、部署的唯一规范源为 `deploy/AGENTS.md`，完整要求均在该文件。本技能及后续 references 仅提供操作方法、示例和排坑资料，不新增或覆盖规范；入口登记和 README 只提供实现清单与材料导航。

- 新增服务端/依赖入口为`deploy/release/<架构>/{server,dependencies}/`，客户端入口为`deploy/release/clients/<架构>/<批次>/`。旧packages/history及deploy根clients仅历史或内部实现。构建工具在build-tools，服务端按已批准Actions原生架构路线执行，本机不启动Docker或用WSL组包；客户端工具仍在Windows。
- 开始时记录目标OS/架构/origin、来源、服务/补丁/客户端范围和终点；用户已确认项不重复提问。“继续到可安装”意味着连续完成整批验证，非每小步请求继续。
- 从当前源码构建=工作区应用源码+公开依赖/基镜像；不扩展为所有依赖源码重编译。记录实际commit/dirty、基镜像、依赖与产物身份；保留原env/锁文件，不运行audit fix、不擅升依赖、不以发布应用镜像替代源码构建。
- 只做当前里程碑。安全扫描发现问题如实列风险，不自动进入无限CVE/软件包整改；新高风险工作或具体阻塞才询问，其他独立工作继续推进。
- 四个状态分别报告：材料齐备、服务器包可安装、目标已安装、客户端/媒体完整验收。`READY_FOR_INSTALL`只能在全系统隔离环境实际完成无外网依赖安装、空store七镜像导入、包内原入口初始化/启动、严格TLS/API/BOSH/WS/可用桥后发布；已有缓存、userspace容器、单测数量不能替代。
- 合格新版本仅交付到 `deploy/release/<架构>/server/<批次>/` 并复核摘要，更新README实际状态。候选归档或Actions链接不是release；历史包和日志不改字节、不顺带删重。
- CA私钥/真实.env/数据库不出目标，客户端仅用目标新CA公开根，VM测试CA不得复用。可安装≠目标实装≠媒体验收≠生产安全批准。报告实际门禁与剩余事项，不编造总进度百分比。
- 本地归并/打包不授权连接或清理服务器。115等目标的备份和精确删除/保留清单须实际核验并获得二次确认；202/118、旧部署目录和现有缓存保持不动。

## 1. 首先询问打包选择

实际构建前先询问以下项目。用户本次已明确的值直接复述确认，只补问缺项，不从历史实例、旧交付包或本机环境代替用户决定。仅编写方案时不执行构建；缺失项列为待确认，先形成带假设的草案：

| 必问项 | 需要确认的内容 |
|---|---|
| 目标架构 | **amd64、arm64，还是双架构分包？** 目标 CPU 平台（海光/兆芯=amd64，鲲鹏/飞腾=arm64，龙芯=不支持需单独评估），不能猜 |
| 容器引擎 | 目标机是 **Docker、Podman 还是 iSulad**？版本？还是完全未装、需要安装器兜底？ |
| 来源路线 | **从当前源码构建，还是拉取已发布 Docker 镜像？** 源码版本/分支，或仓库、tag/digest、访问权限 |
| 入口配置方式 | **烘焙固定 origin**（内网地址已确定，包内直接可用），还是**安装时渲染**（安装脚本交互收集 IP/域名/端口）？ |
| 包类型 | **首装全量包**，还是**增量更新包**（仅变化镜像/产物，须声明基线版本及 digest）？ |
| 服务与补丁范围 | 全栈七服务还是部分？补丁从本技能 [补丁登记表](references/patches.md) 逐项选定，标"包含/不适用/待确认" |
| 客户端 | 是否随包附带 Electron MSI / Android APK？客户端信任配置（内嵌私有 CA 根）是否已确认 |
| 合规材料 | 是否需要 SBOM、离线漏洞扫描报告、包签名（GPG/minisign）？ |
| 介质与分卷 | 交付介质（U盘/光盘/单向网闸）、单卷大小限制、目标侧解压能力（有无 zstd） |
| 构建／导出机 | 用本机还是哪台**有网服务器**构建、验证候选并导出镜像及依赖？明确主机、系统版本、架构、连接方式、Docker和磁盘；不默认用本机Docker或历史服务器 |

证书与秘密的默认立场（直接告知用户，不逐项问）：隔离内网无 ACME，采用 Caddy `tls internal` 私有 CA，**CA 私钥与根证书在安装时于目标机生成，绝不随包**；`.env` 真实秘密不随包，只带 `.example` 模板；客户端信任通过客户端包内嵌根证书或安装时导入实现。甲方若有内部/政务 CA，证书文件同样不随包，安装时挂载。

**首次响应示例（尚未给参数时）：**
> 目标架构是 amd64、arm64 还是双架构？目标机容器引擎是什么？从当前源码构建还是拉取已发布镜像？入口 origin 烘焙进包还是安装时渲染？首装全量包还是增量更新包？另请确认服务/补丁范围、是否附带客户端、合规材料要求、分卷限制和构建机。我会列出包内容清单和坑后执行。

使用提问工具时可分组询问；不得自行选中历史服务器、镜像仓库、旧安装包或上次交付的内容物。

## 1.1 编译打包边界

先询问两种服务器角色，用户已指定则直接复述，不反复询问。构建／导出机与离线验证机可以相同，也可以不同；115只是历史实例，不能作为默认目标。仅更新技能或编写方案不连接服务器。

### 编译打包流程（仅材料交付）

交付Docker部署包，不包含宿主操作系统，不要求麒麟ISO；包级安装资格不作为出包门禁。宿主兼容性前提写入INSTALL，不能仅凭发行版名称宣称兼容。流程只有编译/复用、组包、材料完整性校验、输出release包，不准备测试环境或执行安装/运行测试。

1. 固定已有批次参数和来源；本批在Actions原生aarch64编译组包，复用可核验镜像，仅重建受影响组件。
2. 按目标架构准备镜像、配置、补丁、公共安装入口、Docker/Compose依赖材料、INSTALL和SHA256；已有引擎前提明确，不隐式联网补包。
3. 生成最终归档，核对成员/架构/配置引用/摘要/无秘密；不启动服务，不执行坏包负例或实际安装。
4. 下载完整包到release并复核摘要，报告实际路径、来源、内容及限制。现有READY拒绝逻辑须修复，不能篡改状态冒称已实现；不增加安装测试门禁。


## 2. 探测并生成本次打包清单

定位工作区，阅读根 `AGENTS.md` 及本次渲染所用的 Compose/env 模板（位置以工作区实际为准）。以**本次渲染的 Compose** 为准枚举镜像和工件，不从旧包清单或文档快照照搬（[镜像与工件清单](references/image-inventory.md) 是核对基线，不是内容默认）。

检查构建机：OS/架构、Docker/Buildx 版本、可用磁盘（预计产出见清单，不足先报告）、拉取凭据。Windows 构建机注意换行符与路径分隔符进入安装脚本的问题。

输出脱敏打包清单（后续命令只能使用本清单的值，不拼入历史地址）：

```yaml
target: { arch: <amd64|arm64|multi>, engine: <docker|podman|isulad|to-install>, os_family: <系统或未知> }
source_mode: <source|registry>
origin_mode: <baked|install-time>
public_origin: <烘焙模式时明确写出；安装时模式写 placeholder>
bundle_type: <full|incremental>
base_release: <增量包的基线版本及各镜像基线 digest；全量包为 none>
release: <源码版本或每服务镜像 digest>
services: <本次包含服务、排除服务>
patches: <P01–P08 逐项状态>
clients: { electron: <bool>, android: <bool>, trust_mode: <内嵌CA根|安装时导入|无> }
compliance: { sbom: <bool>, vuln_scan: <bool>, sign: <bool> }
media: { split_size: <如4G或none>, transport: <介质说明> }
builder: { host_arch: <构建机架构>, disk_free: <GiB> }
build_export_host: { host: <本机或本次指定服务器>, os: <版本>, arch: <架构> }
offline_validation: { enabled: <bool>, host: <本次指定服务器或none>, os: <版本>, arch: <架构>, clean_install: <bool>, cleanup_approved: <false直到二次确认>, egress_mode: <待确认或实际隔离方式> }
```

## 3. 先解释"包里会有什么"，再请求确认

阅读 [包结构与安装器规范](references/bundle-spec.md)，按本次清单逐项列出：

| 工件 | 作用 | 本次动作（拉取/构建/复用/模板） | 架构 | 身份（digest/SHA256） | 已知坑 | 验证方法 |
|---|---|---|---|---|---|---|
| jitsi web/prosody/jicofo/jvb 镜像 | 会议栈 | 待确定 | 待确定 | 待确定 | 架构匹配/DTLS兼容 | manifest 与 digest 复核 |
| app-web/api 镜像或产物 | 业务栈 | 待确定 | 待确定 | 待确定 | 业务镜像未必多架构 | 同上 |
| gateway（caddy/nginx）镜像 | TLS 与路由 | 待确定 | 待确定 | 待确定 | DNS 插件版不能用标准镜像冒充 | 模块核对 |
| 补丁工件 | P01–P08 选中项 | 待确定 | 架构无关 | 待确定 | 版本变化旧补丁不可自动套用 | 摘要与来源核对 |
| compose/env 模板 | 目标机配置 | 渲染 | — | — | 不含秘密、不含历史地址 | 渲染审查 |
| install.sh/uninstall.sh | 安装器 | 生成 | 按引擎适配 | — | 引擎探测、时钟检查 | 构建机演练/干跑 |
| bin 兜底工具 | 无 compose 插件目标机 | 下载对应架构静态二进制 | 按目标 | 官方来源摘要 | 来源可信、架构正确 | 摘要复核 |
| 客户端安装包 | 桌面/移动端 | 待确定 | — | 待确定 | 信任配置与本次 CA 方案一致 | 摘要与构建记录 |
| 合规材料 | SBOM/漏扫/签名 | 待确定 | — | — | 工具缺失报阻塞不静默安装 | 报告内容抽查 |

必须逐镜像核对 manifest 支持目标架构并锁定 digest；官方 Jitsi 多架构不代表业务镜像也多架构，发现不匹配标阻塞，不静默跨架构模拟（QEMU 构建须经用户明确批准并在报告中标记）。业务镜像未发布时不得编造仓库地址，提供"授权源码构建"或"用户提供同源包"选项。增量包必须声明基线版本与各镜像基线 digest，缺基线先澄清，不做"全量冒充增量"。确认后不再逐项重复索取相同授权。

## 4. 按路线执行构建与组装

### A. 源码路线

1. 记录相关子项目 commit/dirty 状态，测试并构建本次候选：API 通常 `mvn -B test package`；业务 Web 构建后执行既有 WebView 语法检查。构建变量来自本次入口选择，保留用户原配置文件，检查生成 JS 不含错误环境的有效 iframe origin。
2. 按已确认服务范围从工作区应用源码构建，包含所要求Jitsi项目，不以官方预构建应用镜像替代。允许公开依赖与基础运行时镜像，不要求编译全部传递依赖。
3. 服务器JAR/静态资源和镜像均按本批批准构建路线执行；47批次仅Actions原生aarch64，本机只做编辑和无Docker辅助检查。原生依赖/基础镜像匹配目标架构。
4. 独立 staging 目录、产物 SHA256、发布清单；旧包不能冒充新版本。

### B. 已发布镜像路线

1. 请用户提供或确认可信仓库地址、tag/digest、凭据引用和发布说明；不能编造仓库或宣称镜像已发布。
2. `docker pull --platform` 按目标架构拉取，核对每镜像 manifest 支持目标架构、锁定 digest 与组件兼容组合；不静默使用跨架构模拟。
3. 核对镜像内是否已含所需补丁（按 [补丁登记表](references/patches.md) 逐项检查），不重复注入、不猜文件布局；必须修改镜像内容时优先受支持的持久挂载，需派生镜像则解释并获准，不暗中改成源码路线。
4. 镜像源失败/网络慢不得以不可信镜像代替；平台/权限不满足报告阻塞，提供换版本、授权源码构建或用户提供同源校验包的选项，不擅自切换。

### 两条路线共同要求

- **拉取即锁定**：每个镜像记录 `repo:tag → digest → arch → size → 来源`，写入包的 `manifest.json`；floating tag 不能作为唯一身份。
- **按架构分包**：`images-amd64.tar.zst` / `images-arm64.tar.zst` 独立产出，构建机架构不等于目标架构，必须用 `--platform` 或 buildx，装包后 `docker inspect` 复核 tar 内各镜像架构。
- **补丁工件**：从 [补丁登记表](references/patches.md) 登记的源路径复制，核对存在性与摘要；版本变化后不自动沿用旧补丁，差异说明并暂停不兼容项。
- **配置模板**：只含 `.example` 与渲染脚本；烘焙模式的 origin 来自本次清单；扫描包内不得出现真实秘密、CA 私钥、历史实例地址（用清单值 grep 反查）。
- **安装器与校验**：按 [包结构与安装器规范](references/bundle-spec.md) 生成 install.sh（时钟检查→引擎探测→SHA256 校验→load→digest 复核→（安装时模式）收集 origin 渲染 env→compose up→冒烟→验收报告）与 uninstall.sh；禁止全局 prune、禁止无范围 `down -v`、不影响非本项目资源。
- **合规材料**：SBOM 用 syft、漏扫用 trivy 离线库；工具缺失逐项报阻塞并请求允许安装，不静默装软件，不用 Markdown 冒充 xlsx。签名私钥不随包，验证公钥随包。
- **组装后校验**：重算SHA256SUMS，核对归档成员、镜像架构、配置引用及必需材料；分卷重组后摘要须一致。不启动容器演练、不执行安装运行测试；材料校验失败不交付。

## 5. 构建中逐工件报告进度

维护全工件状态表，状态为 `待处理/获取中/构建中/校验中/已通过/失败/阻塞/跳过`。每个工件开始、阶段完成、失败时输出一次简短更新：

```text
[4/9][jvb镜像][获取中] 已按 linux/arm64 拉取，正在核对 digest 与 manifest 架构。
[4/9][jvb镜像][校验中] digest 匹配来源，正在写入 manifest.json。
[4/9][jvb镜像][已通过] 架构/摘要/大小复核通过。
```

示例不是执行证据，实际输出必须基于工具结果，不虚构百分比/摘要。失败要指出对后续工件的阻塞及下一步，依赖它的组装与校验不得继续报绿。

## 6. 组装完成后逐项给验证结果

报告 `通过/失败/阻塞/未验证/不适用`，每项含预期、实际、证据位置/命令退出码：

| 验证 | 关键检查 |
|---|---|
| 架构匹配 | 每镜像 manifest/inspect 架构与目标一致；无静默模拟产物 |
| 身份与完整性 | digest 与来源一致；SHA256SUMS 全量复算通过；签名（如要求）验证通过 |
| 内容审查 | 包内无秘密、无 CA 私钥、无历史实例地址；补丁工件摘要与登记一致 |
| 安装器 | 时钟/引擎探测逻辑、（安装时模式）渲染结果不含占位残留；有条件时构建机演练通过 |
| 分卷还原 | 切分→重组→校验一致 |
| 文档一致性 | manifest、安装手册、清单三者版本/架构/内容一致 |

**打包完成不等于目标安装通过**：交付实际release路径、SHA256、架构/origin、内容清单、INSTALL及前置条件；不以Actions绿灯或链接代替本地包，不附加独立首装测试门禁。
